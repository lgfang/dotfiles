* Shared instructions

#+begin_src markdown-ts :tangle no :noweb-ref shared-instructions
  # General AI Coding Instructions

  ## Plan before implementing

  Before making any code changes, briefly state your plan: what files you
  intend to modify, what approach you'll take, and any trade-offs. Wait for
  my confirmation before proceeding. Skip this for trivial one-line fixes or
  when I've already specified the exact change.

  ## Scratch / temp files

  Write scratch and intermediate files under `<repo_root>/agent-scratch/` (create
  the directory if needed). Use `/tmp/agent-scratch/` only for data that may be
  lost, since it is cleared on reboot.

  ## Headless hosts (no browser / GUI)

  If this host is headless, interactive browser-based auth flows hang silently:
  a tool may fail simply because it is blocked waiting on an SSO/OIDC login it
  can't open a browser for. Any such login must be done out-of-band with a
  device-code or `--no-browser` flow, then restart/retry.

  - DevProd MCP Gateway auth failures (e.g. the `mdb-devprod` MCP showing
    "Failed to connect", hanging on authentication): re-authenticate with
    the tool-specific command (e.g. `opencode mcp auth mdb-devprod`,
    `codex mcp login mdb-devprod`), then restart the agent. On a headless
    host, see the headless MCP auth section in ai.org.

  ## Git & GitHub

  1. Run `git commit --amend` and `git push` as standalone commands, never chained
     with other operations. They often require explicit approval, and chaining
     would hold the other commands hostage to that approval.

  2. Do not amend a commit that has already been pushed, create a new commit
     instead. Amend only unpushed commits.

  3. Never post a PR review output (top-level review bodies, inline review
     comments and replies to review comments etc.) without my explicit
     confirmation. Draft the full text and show it to me first every time.

  4. When posting PR review comments, create them as a pending (draft) review so I
     can review and submit them myself. Only submit the review directly if I
     explicitly ask.
     - `gh pr review` has no draft mode per its official manual. Use the GitHub REST
       API: `POST /repos/{owner}/{repo}/pulls/{n}/reviews` with a body and no event
       field (omitting event defaults to PENDING). Never pass
       event=COMMENT/APPROVE/REQUEST_CHANGES without my explicit go-ahead.
#+end_src

* Agent skills

Skill repositories are cloned under =~/.agents/=, with one subdirectory per
source repository. Individual skills are symlinked into each tool’s skills
directory (=~/.claude/skills/= and =~/.config/opencode/skills/=), allowing all
supported agents to discover the same skills.

This approach was chosen over the Claude Code plugin marketplace for two
reasons:

1. *Cross-tool compatibility* — OpenCode and other agents do not have a plugin
   system, but they can read skills from a local directory. Symlinks work across
   tools, whereas plugins are specific to Claude Code.

2. *Simplicity* — There is one clone per repository and one symlink per skill,
   with no marketplace manifests or plugin-cache paths that change after every
   update. To update a skill repository, simply run =git pull=; the symlinks
   continue to point to the updated files automatically.

When you need to install or update skills, *ask an agent to handle it for you*.

Claude configuration files:
- =~/.claude/settings.json= :: User-level configuration file. Applies globally
  to Claude Code sessions for the current operating-system user, unless
  overridden by project-level or local settings.

- =~/.claude/remote-settings.json= :: Remote or account-managed user
  configuration file. Treat this as policy managed by the organization: local
  changes are reverted when a Claude session starts.
  + Note: Claude load permission lists before reverting this file, so edits
    affect the first session after the change.

  configuration file, meant to be checked in version control.

  constant unwanted diffs.

#+end_src

IMPORTANT: Use the ~Bash(cmd:*)~ form, not ~Bash(cmd *)~. The =:*= is Claude
Code's prefix-match operator, which parses the command and validates each
subcommand (split on ~;~, ~&&~, ~|~, etc.) separately. The space + bare =*= is a
literal glob over the whole command string, so it also matches chained/injected
commands like ~grep foo; rm -rf ~~ or ~$(...)~ substitutions — an easy way to
auto-approve arbitrary execution.

** Global permissions

Codex's execpolicy rules (=prefix_rule=) control which commands may run
outside the sandbox without prompting.  The file lives at
=~/.codex/rules/default.rules= and uses Starlark syntax.  See
https://developers.openai.com/codex/agent-configuration/rules and the
parser source at =codex-rs/execpolicy/src/parser.rs=.

Key differences from Claude/OpenCode permission lists:

- =prefix_rule= matches command-token *prefixes* — there is no =:*= glob;
  =pattern = ["git"]= is equivalent to Claude's =Bash(git:*)=.
- *Most restrictive wins*: =forbidden= > =prompt= > =allow=.  This means a
  broad =prompt= rule would override a narrower =allow=, so the
  =.poetry/bin/poetry run:= ask rule from Claude/OpenCode is omitted here;
  its narrow =allow= children suffice, and unmatched =poetry run= commands
  fall back to the default approval policy (prompt under =on-request=).
- =prefix_rule= cannot express mid-pattern wildcards.  The Claude/OpenCode
  rules =gh api repos/*/files:= and =gh api repos/*/comments:= are
  therefore deferred — add more specific rules once the exact repo patterns
  are known.
- In-sandbox commands (workspace reads/writes) are governed by
  =sandbox_mode= + =approval_policy=, not by rules.  Rules only apply when
  a command escapes the sandbox (e.g. needs network or writes outside the
  workspace).

  <<codex-rules>>
#+end_src

All blocks share =:noweb-ref codex-rules= and are accumulated in document
order into the rules file.

** Global permissions

#+begin_src json-ts :tangle no :noweb yes :noweb-ref opencode-permissions
  "permission": {
    "bash": {
      "*": "ask",
      <<opencode-perm-bash>>
      "true": "allow"
    },
    <<opencode-perm-external>>,
    <<opencode-perm-web>>,
    <<opencode-perm-skill>>,
    <<opencode-perm-mcp>>
    "true": "allow"
  }
#+end_src

Opencode's bash permission uses ="cmd *": "action"= glob patterns with *last
match wins*. A leading ="*": "ask"= catch-all makes any unmatched command prompt
instead of falling back to opencode's default =allow=; every rule below
overrides it for the commands it matches. Rules are grouped by command/tool:
within each group broad =allow= rules come before narrower =ask= overrides so
the ask wins on overlap. All blocks share =:noweb-ref opencode-perm-bash=
and are accumulated in document order into the =bash= object.

* Authenticate an MCP server on a headless host
:PROPERTIES:
:CUSTOM_ID: headless-mcp-auth
:END:

The OAuth callback of a remote MCP server (e.g. =mdb-glean=) opens a listener on
the headless host, so completing the flow needs an SSH port forward. The steps
below are common to Claude, Codex and OpenCode; only the command in step 1
differs per tool.

1. On the headless host, trigger the MCP authentication. The command depends on
   the tool, e.g. for OpenCode:
   #+begin_src sh
     opencode mcp auth mdb-glean
   #+end_src
2. Open the printed authorisation URL in your local browser.
3. Complete authentication. The browser will redirect to the OAuth callback URL,
   usually =http://localhost:<port>/...=, and fail because the callback listener
   is running on the headless host.
4. From your local machine, create an SSH local port forward to the headless
   host. Replace =19876= with the port from the actual callback URL:
   #+begin_src sh
     ssh -N -L 19876:localhost:19876 user@headless-host
   #+end_src
5. Reload the failed callback URL in your browser.
